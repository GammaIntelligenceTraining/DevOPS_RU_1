## Станция 1: Файловая система, поиск и потоки ввода-вывода

### Пример 1.1: Механика флагов утилиты `ls` и видимость метаданных

В этом упражнении вы исследуете вывод утилиты `ls`, анализируя отображение метаданных, скрытых файлов, атрибутов каталогов и сортировку по размеру с использованием различных комбинаций флагов.

#### Разбор флагов утилиты `ls`:

| Флаг / Опция | Техническое описание и механика | Применение в эксплуатации и DevOps |
| :--- | :--- | :--- |
| `(Без флагов)` | Базовый вывод содержимого каталога; выводит только имена видимых файлов в несколько колонок. | Быстрая визуальная проверка содержимого каталога, когда подробные метаданные не требуются. |
| `-l` | Длинный формат вывода; отображает тип файла, права доступа, число жестких ссылок, владельца, группу, размер в байтах и дату изменения. | Базовый диагностический инструмент для проверки прав доступа и владельцев файлов в системе. |
| `-a` (--all) | Отображает скрытые файлы (имена которых начинаются с точки `.`, включая `.` и `..`). | Обязателен при проверке домашних директорий, файлов конфигурации и корней репозиториев (`.git`, `.env`). |
| `-d` (--directory) | Выводит метаданные самого каталога, не раскрывая его внутреннее содержимое. | Незаменим для проверки прав доступа и владельца узла каталога (критично для диагностики прав обхода). |
| `-h` (--human-readable) | Масштабирует размеры файлов в удобные для чтения единицы (K, M, G, T) на основе степеней 1024. | Используется в паре с `-l` для быстрого обнаружения аномально больших файлов логов при нехватке места на диске. |
| `-S` | Сортирует содержимое каталога по размеру в порядке убывания (сначала самые большие файлы). | Позволяет быстро выявить файлы, переполняющие диск, при передаче в `head` (`ls -lhS \| head -n 10`). |
| `-t` | Сортирует записи по времени изменения в порядке убывания (сначала самые новые файлы). | Необходим при расследовании инцидентов для определения файлов, измененных или добавленных последними. |
| `-r` | Инвертирует порядок сортировки (часто комбинируется как `-rt`, чтобы новые файлы оставались внизу терминала). | Предотвращает уход свежих файлов за пределы экрана в каталогах с большим количеством записей (`ls -lart`). |
| `-R` (--recursive) | Рекурсивно выводит все подкаталоги и вложенные в них файлы вниз по дереву. | Быстрый аудит небольших директорий без переключения на специализированную утилиту `find`. |
| `-i` (--inode) | Выводит внутренний номер индексного дескриптора (inode) каждого файла. | Применяется для обнаружения жестких ссылок с одинаковым инодом и диагностики исчерпания инодов (`df -i`). |
| `-1` (Цифра один) | Принудительно выводит по одному имени файла на строку без форматирования и цветов. | Оптимален для циклов в bash-скриптах и передачи имен файлов через конвейер (`ls -1 /opt/bin \| xargs ...`). |

### Пример 1.2: Точная фильтрация текста с помощью `grep`

Выполните блок команд ниже для создания тестового файла логов, содержащего сообщения разного уровня важности, предупреждения и события healthcheck:
```bash
# Создание каталога (-p: создавать родительские каталоги при отсутствии)
sudo mkdir -p /tmp/app_logs
# Запись многострочного тестового лога через Here-Document в обход ловушки sudo
cat << 'EOF' | sudo tee /tmp/app_logs/production.log >/dev/null
[2026-09-13 10:01:02] INFO Application initialized successfully
[2026-09-13 10:01:15] WARN Database latency high: 450ms
[2026-09-13 10:01:22] ERROR Connection timeout to payment gateway: 504
[2026-09-13 10:01:30] CRITICAL Out of memory condition detected in worker pool
[2026-09-13 10:01:45] info Heartbeat ping received from healthcheck probe
EOF
```

В ходе занятия вы на практике сравните чувствительный к регистру поиск, флаг игнорирования регистра (`-i`), инвертирование условий поиска (`-v`) и рекурсивный поиск по шаблонам регулярных выражений (`-rnE`).

#### Разбор флагов утилиты `grep`:

| Флаг / Опция | Техническое описание и механика | Применение в эксплуатации и DevOps |
| :--- | :--- | :--- |
| `(Без флагов)` | Поиск точного совпадения строки с учетом регистра символов в файле или потоке. | Стандартный поиск, когда регистр целевой строки известен заранее. |
| `-i` (--ignore-case) | Игнорирует регистр символов как в шаблоне, так и во входных данных. | Стандарт при разборе логов, где уровни важности могут быть записаны по-разному (`ERROR`, `Error`, `error`). |
| `-v` (--invert-match) | Инвертирует условие совпадения; выбирает все строки, не содержащие указанный шаблон. | Незаменим для фильтрации фонового шума (например, `grep -v "healthcheck"`), изолируя аномалии. |
| `-r` / `-R` (--recursive) | Рекурсивный поиск по всем файлам внутри вложенных каталогов (`-R` следует по симлинкам). | Поиск по всей иерархии логов (например, `grep -r "timeout" /var/log/nginx/`). |
| `-n` (--line-number) | Добавляет перед каждой найденной строкой ее порядковый номер в исходном файле. | Ускоряет отладку, указывая точный номер строки для последующего редактирования в `nano` или `vim`. |
| `-E` (--extended-regexp) | Включает расширенные регулярные выражения (ERE), поддерживая операторы `\|`, `+`, `?`, `()`. | Позволяет искать несколько условий в одном запросе (например, `grep -E "FATAL\|PANIC\|OOM"`). |
| `-c` (--count) | Подавляет стандартный вывод строк и выводит общее число совпадений. | Быстрое получение числовых метрик для проверок мониторинга без передачи в `wc -l`. |
| `-l` (--files-with-matches) | Выводит только имена файлов, содержащих хотя бы одно совпадение, останавливаясь на первом. | Сканирование сотен файлов конфигурации для поиска серверов, использующих заданную директиву. |
| `-L` (--files-without-match) | Выводит только имена файлов, в которых совпадений НЕ обнаружено. | Аудит соответствия стандарту (например, поиск виртуальных хостов без SSL-директив). |
| `-w` (--word-regexp) | Ищет только точные совпадения с целым словом, ограниченным границами слов. | Предотвращает ложные срабатывания при поиске имен переменных или портов (поиск `port 80`, но не `8080`). |
| `-A`, `-B`, `-C <N>` | Вывод контекста: печатает `<N>` строк после (`-A`), до (`-B`) или вокруг (`-C`) найденной строки. | Анализ стека вызовов вокруг точки сбоя приложения в логах (`grep -C 5 "Exception"`). |
| `-F` (--fixed-strings) | Интерпретирует шаблон как простую фиксированную строку, отключая механизм регулярных выражений. | Высокопроизводительный поиск строк со спецсимволами (IP-адреса, URL, знаки `.*`). |

### Пример 1.3: Поиск файлов и создание архивов

В этом упражнении вы будете использовать утилиту `find` для выборки файлов по имени, типу и правам доступа, а затем упаковывать и анализировать архивы с помощью `tar`.

#### Разбор флагов для `find` и `tar`:

| Команда / Флаг | Техническое описание и механика | Применение в эксплуатации и DevOps |
| :--- | :--- | :--- |
| `find -type f` | Ограничивает поиск только регулярными файлами, исключая каталоги, симлинки и сокеты. | Защищает скрипты пакетной обработки от непреднамеренного изменения каталогов. |
| `find -name <шаблон>` | Поиск по имени файла на основе shell-маски (с учетом регистра). | Стандартный способ поиска файлов в Linux (например, `find /var/log -name "*.log"`). |
| `find -perm <маска>` | Поиск по точному восьмеричному значению маски прав (например, `777` для `rwxrwxrwx`). | Инструмент аудита безопасности для обнаружения файлов и папок с избыточными правами. |
| `tar -c` (--create) | Инициализирует создание нового архива tar. | Базовая операция упаковки логов, конфигураций или исходного кода для деплоя и бэкапов. |
| `tar -z` (--gzip) | Пропускает архив через компрессор `gzip` при создании или распаковке. | Создает сжатые архивы `.tar.gz` для экономии дискового пространства и сетевого трафика. |
| `tar -v` (--verbose) | Подробный вывод; отображает путь к каждому упаковываемому или распаковываемому файлу. | Визуальный контроль выполнения операции в терминале. |
| `tar -f <файл>` (--file) | Указывает путь к файлу архива на диске (должен стоять непосредственно перед именем архива). | Обязательный флаг, направляющий архив в файл на диске, а не на ленточный накопитель по умолчанию. |
| `tar -t` (--list) | Выводит список содержимого архива без его распаковки на диск. | Предварительная проверка содержимого архива во избежание перезаписи локальных данных. |
| `find -mtime <+/-N>` | Фильтрует файлы по времени изменения с шагом в 24 часа (`-7` = за последние 7 дней). | Автоматическая очистка старых логов (например, `find /tmp -type f -mtime +30 -delete`). |
| `find -size <+/-N>` | Фильтрует файлы по размеру (`+100M` = файлы крупнее 100 мегабайт). | Экстренный поиск при переполнении диска до 100% для обнаружения разросшихся файлов. |
| `find -user / -group` | Находит файлы, принадлежащие конкретному пользователю или группе (UID/GID). | Поиск файлов, оставшихся от удаленных или неавторизованных учетных записей. |
| `find -maxdepth <N>` | Ограничивает глубину рекурсивного обхода каталогов значением `<N>`. | Предотвращает зависание при поиске по гигантским файловым системам или сетевым дискам. |
| `find -exec <команда> {} +` | Запускает внешнюю команду для найденных файлов, группируя пути в аргументе `{}`. | Высокопроизводительная пакетная обработка (например, `find /var/www -type d -exec chmod 755 {} +`). |
| `tar -x` (--extract) | Извлекает файлы из архива tar в текущую файловую систему. | Развертывание релизов приложений или восстановление резервных копий. |
| `tar -C <каталог>` | Переходит в указанный каталог перед выполнением распаковки архива. | Извлечение архива в конкретный целевой каталог без замусоривания текущей директории. |
| `tar --exclude=<маска>` | Исключает файлы по шаблону при создании архива. | Исключение временных каталогов кэша, веток `.git` и `node_modules` из архива проекта. |

### Пример 1.4: Перенаправление потоков и Here-Documents

Выполните приведенные ниже команды для практической отработки разделения потоков вывода, дописывания журналов и изоляции сообщений об ошибках:
```bash
# Создание каталога для изоляции учебных файлов (-p: создавать родительские каталоги при отсутствии)
mkdir -p /tmp/stream_lab

# Перенаправление стандартного вывода (stdout, FD 1) с перезаписью файла
ls /tmp/app_logs /nonexistent_directory > /tmp/stream_lab/output.log

# Дописывание строки в конец файла без удаления существующего содержимого (оператор >>)
echo "Status check: OK" >> /tmp/stream_lab/output.log

# Изоляция потока ошибок (stderr, FD 2) в отдельный файл журнала
ls /tmp/app_logs /nonexistent_directory 2> /tmp/stream_lab/error.log

# Дописывание новых сообщений об ошибках в существующий журнал сбоев (оператор 2>>)
ls /missing_path 2>> /tmp/stream_lab/error.log
```

Выполните команды ниже для объединения потоков вывода и подавления ненужных сообщений через псевдоустройство /dev/null:
```bash
# Объединение stdout и stderr в единый лог через синтаксис Bash (&>)
ls /tmp/app_logs /nonexistent_directory &> /tmp/stream_lab/combined_bash.log

# Универсальное POSIX-объединение потоков (stdout в файл, stderr дублируется в дескриптор 1 через 2>&1)
ls /tmp/app_logs /nonexistent_directory > /tmp/stream_lab/combined_posix.log 2>&1

# Перенаправление ошибок в конвейер через 2>&1 для последующей фильтрации утилитой grep
ls /tmp/app_logs /nonexistent_directory 2>&1 | grep "nonexistent"

# Подавление всего вывода (stdout и stderr в /dev/null) для тихих фоновых проверок сервисов
/usr/bin/systemctl is-active nginx >/dev/null 2>&1 && echo "Nginx is running"

# Подавление сообщений об ошибках (find: -name — поиск по маске имени; head: -n 5 — вывод первых 5 строк)
find /etc -name "*.conf" 2>/dev/null | head -n 5
```

Выполните команды ниже для передачи данных в стандартный ввод команды через файловый дескриптор 0 и Here-String:
```bash
# Перенаправление содержимого файла на вход утилите (wc: -l — подсчет только количества строк)
wc -l < /tmp/stream_lab/output.log

# Прямая передача строки в процесс без создания промежуточной подоболочки echo (Here-String <<<)
tr '[:lower:]' '[:upper:]' <<< "error: connection reset by peer"
```

Выполните команды ниже для разветвления потоков данных на экран и в файл с помощью утилиты tee:
```bash
# Отображение информации о времени работы системы в терминале с одновременным сохранением в файл через tee
uptime | tee /tmp/stream_lab/uptime.log

# Дописывание новых данных в файл без затирания с сохранением вывода на экран (tee: -a — режим append)
date | tee -a /tmp/stream_lab/uptime.log
```

Выполните команды ниже для воспроизведения ловушки sudo и записи защищенных файлов конфигурации через sudo tee:
```bash
# Создание защищенного тестового файла с ограниченным доступом (chmod: 600 — чтение и запись только владельцу)
sudo touch /tmp/root_protected.conf
sudo chmod 600 /tmp/root_protected.conf

# Попытка записи через sudo с перенаправлением завершается системной ошибкой Permission denied
sudo echo "cluster_id=42" > /tmp/root_protected.conf 2>&1 || echo "Ловушка сработала: оболочка открыла файл до sudo"

# Корректная запись в защищенный файл через конвейер и утилиту sudo tee
echo "cluster_id=42" | sudo tee /tmp/root_protected.conf >/dev/null

# Безопасное дописывание параметров в защищенный файл с правами суперпользователя (tee: -a — режим append)
echo "node_role=master" | sudo tee -a /tmp/root_protected.conf >/dev/null

# Принудительное удаление временного файла (rm: -f — удаление без запроса подтверждения)
sudo rm -f /tmp/root_protected.conf
```

Выполните команды ниже для создания многострочных конфигураций через Here-Documents с буквальной обработкой и динамической подстановкой переменных:
```bash
# Запись файла конфигурации с сохранением символов доллара без раскрытия переменных (кавычки 'EOF')
cat << 'EOF' | sudo tee /tmp/stream_lab/service.env >/dev/null
NODE_ENV=production
PORT=8080
DB_HOST=127.0.0.1
CACHE_DRIVER=redis
SYSTEM_TOKEN=${SECRET_TOKEN_VAR}
EOF

# Генерация файла с автоматической подстановкой текущих переменных окружения хоста (date: -u — формат времени UTC)
cat << EOF | sudo tee /tmp/stream_lab/host_identity.env >/dev/null
GENERATED_BY=$USER
GENERATED_ON=$(hostname)
USER_ID=$UID
GENERATED_AT=$(date -u +"%Y-%m-%dT%H:%M:%SZ")
EOF

# Рекурсивное принудительное удаление учебной рабочей директории (rm: -r — рекурсивно, -f — force)
rm -rf /tmp/stream_lab
```

#### Разбор операторов перенаправления потоков:

| Оператор / Синтаксис | Техническое описание и механика | Применение в эксплуатации и DevOps |
| :--- | :--- | :--- |
| `>` | Перенаправляет файловый дескриптор 1 (stdout) в целевой файл с его перезаписью. | Запись вывода команды в лог или очистка файла перед сохранением свежего состояния. |
| `2>` | Перенаправляет файловый дескриптор 2 (stderr) в файл; stdout остается нетронутым. | Изоляция сообщений об ошибках в отдельный журнал без смешивания с обычными данными. |
| `&>` | Синтаксис Bash, объединяющий stdout (1) и stderr (2) в один целевой файл. | Стандартный прием для заданий cron, чтобы зафиксировать весь вывод программы в одном логе. |
| `<< 'EOF'` (В кавычках) | Here-Document с буквальной обработкой; отключает подстановку параметров и переменных. | Безопасная запись скриптов и конфигураций, содержащих знак `$`, без их преждевременного раскрытия. |
| `\| sudo tee <файл>` | Читает stdin и записывает в файл с правами суперпользователя в обход ловушки sudo. | Создание и редактирование конфигурационных файлов в `/etc/` или `/var/www/` без текстового редактора. |
| `>>` | Дописывает дескриптор 1 (stdout) в конец целевого файла без удаления существующих данных. | Стандартное логирование с сохранением полной истории предыдущих записей. |
| `2>>` | Дописывает дескриптор 2 (stderr) в конец целевого файла без очистки. | Накопление диагностических сообщений об ошибках в журнале сбоев приложения. |
| `2>&1` | POSIX-совместимый способ объединения дескриптора 2 с текущим направлением дескриптора 1. | Перенаправление потоков для скриптов `/bin/sh` (`command > file.log 2>&1`). |
| `<` | Перенаправляет содержимое файла в дескриптор 0 (stdin) целевого процесса. | Загрузка дампов баз данных в клиентские утилиты (`mysql -u root db < dump.sql`). |
| `<< EOF` (Без кавычек) | Here-Document с раскрытием переменных; подставляет значения `$VAR` и вызовы `$(cmd)`. | Динамическая генерация конфигурационных файлов на основе переменных окружения. |
| `<<<` | Here-String; передает одиночную строковую переменную напрямую на вход stdin процесса. | Передача строковых переменных в утилиты без вызова лишних подоболочек `echo \|`. |
| `\| tee -a <файл>` | Разделяет поток: выводит данные в терминал и одновременно дописывает (`-a`) их на диск. | Мониторинг хода выполнения установочных скриптов в реальном времени с логированием на диск. |

### Пример 2.1: Стили вызова `ps`

Выполните блок команд ниже для запуска тестового процесса, потребляющего 100% одного процессорного ядра, в фоновом режиме:
```bash
# Запуск бесконечного цикла в подоболочке bash в фоновом режиме (bash: -c — выполнить строку команд; & — запуск в фоне)

```

В ходе занятия вы на практике сравните стиль BSD (`ps aux`), стиль POSIX (`ps -ef`) и структурированный формат DevOps (`ps -eo ... --sort=-%cpu`).

#### Разбор флагов утилиты `ps`:

| Стиль / Флаг | Техническое описание и механика | Применение в эксплуатации и DevOps |
| :--- | :--- | :--- |
| `aux` (BSD) | Отображает все процессы (`a`), с информацией о пользователях (`u`), включая демоны (`x`). | Индустриальный стандарт для анализа потребления памяти (`%MEM`) и процессора (`%CPU`). |
| `-ef` (POSIX) | Стандартный синтаксис, выводящий все процессы (`-e`) в полном формате (`-f`). | Отображает родительский PID (`PPID`), необходимый для поиска супервизоров и дочерних процессов. |
| `-eo <поля>` | Пользовательский селектор колонок; выводит только явно указанные поля данных. | Формирует предсказуемый табличный вывод для bash-скриптов автоматизации без хрупкого парсинга. |
| `--sort=-%cpu` | Сортирует вывод по убыванию (знак `-`) процента утилизации процессора. | Мгновенно поднимает наиболее ресурсоемкие зависшие процессы наверх списка при авариях. |
| `-u <пользователь>` | Фильтрует таблицу процессов по имени владельца. | Изолирует активность системных демонов (например, `ps -u www-data` или `ps -u postgres`). |
| `-p <PID1,PID2>` | Ограничивает вывод только явно перечисленными через запятую номерами PID. | Точечный аудит процессов, идентификаторы которых уже известны из системных алертов. |
| `-C <команда>` | Выбирает процессы по имени исполняемого бинарного файла (например, `ps -C nginx`). | Быстрая альтернатива фильтрации через `grep` при поиске стандартных демонов. |
| `--forest` / `-H` | Выводит древовидную иерархию связей между родительскими и дочерними процессами. | Анализ связей между мастер-процессами и воркерами (Gunicorn, Celery, Nginx). |
| `-T` | Отображает отдельные потоки выполнения (треды) каждого процесса с номерами `SPID`. | Диагностика взаимных блокировок и аномальной загрузки CPU в многопоточных приложениях. |

### Пример 2.3: Протокол эскалации сигналов

Выполните блок команд ниже для отработки протокола эскалации сигналов: отправка запроса на корректное завершение (`SIGTERM`), проверка статуса и последующее принудительное уничтожение (`SIGKILL`):
```bash
# Шаг 1: Запрос на корректное завершение процесса (kill: -15 — сигнал SIGTERM для штатной остановки)
kill -15 "$ROGUE_PID"

# Шаг 2: Пауза в 2 секунды для корректного освобождения ресурсов
sleep 2

# Шаг 3: Проверка наличия процесса в таблице ядра (ps: -p — фильтрация по конкретному PID)
ps -p "$ROGUE_PID"

# Шаг 4: Принудительное уничтожение процесса ядром при отсутствии реакции (kill: -9 — безусловный сигнал SIGKILL)
kill -9 "$ROGUE_PID"

# Шаг 5: Финальная проверка удаления PID из таблицы процессов (ps: -p — фильтрация по конкретному PID)
ps -p "$ROGUE_PID"
```

В ходе занятия вы изучите технические различия между перехватываемыми программными сигналами и безусловным уничтожением процессов ядром.

#### Разбор сигналов процессов и утилиты `kill`:

| Сигнал / Номер | Техническое описание и механика | Применение в эксплуатации и DevOps |
| :--- | :--- | :--- |
| `SIGTERM` (`15`) | Стандартный перехватываемый сигнал завершения; вызывает обработчик graceful shutdown. | Позволяет приложениям сохранить состояние, завершить активные запросы и удалить lock-файлы. |
| `SIGKILL` (`9`) | Безусловная остановка ядра; немедленно освобождает память процесса без уведомления программы. | Аварийная мера, когда зависший процесс полностью игнорирует стандартный сигнал `SIGTERM`. |
| `SIGHUP` (`1`) | Сигнал обрыва сессии; предписывает демонам перечитать файлы конфигурации без закрытия сокетов. | Применение изменений в конфигурации Nginx, Apache или OpenSSH без простоя сервиса. |
| `SIGINT` (`2`) | Сигнал прерывания с клавиатуры, отправляемый комбинацией клавиш `Ctrl+C`. | Запрос на немедленную корректную остановку запущенной в терминале интерактивной программы. |
| `SIGQUIT` (`3`) | Сигнал выхода, отправляемый через `Ctrl+\`; останавливает процесс и создает дамп памяти (core dump). | Используется разработчиками и SRE для снятия дампа памяти перед отладкой в `gdb`. |
| `SIGSTOP` (`19`) / `SIGCONT` (`18`) | Приостановка и возобновление выполнения процесса без потери его рабочего состояния. | Временная приостановка тяжелых фоновых задач при пиковых нагрузках на веб-сервер. |
| `SIGUSR1` (`10`) / `SIGUSR2` (`12`) | Пользовательские сигналы с кастомной логикой, заложенной разработчиками приложения. | Используются в Nginx для ротации файлов журналов на лету без потери клиентских подключений. |
| `kill -0 <PID>` | Нулевой сигнал; проверяет права доступа и наличие процесса в памяти без отправки сигнала. | Надежная проверка жизнеспособности процесса в bash-скриптах мониторинга (`kill -0 $PID`). |

### Пример 2.4: Управление фоновыми заданиями и устойчивость сессий

Выполните блок команд ниже для запуска фонового скрипта, устойчивого к обрыву сессии терминала с помощью `nohup` и подоболочки `bash -c`:
```bash
# Запуск фонового скрипта, защищенного от сигнала обрыва сессии SIGHUP
# 'nohup': игнорировать сигнал SIGHUP при отключении терминала
# 'bash -c': запуск дочерней подоболочки для выполнения переданной строки команд
# '&': перевод выполнения скрипта в фоновый режим
nohup bash -c 'for i in {1..60}; do echo "Sync step $i" >> /tmp/sync.log; sleep 1; done' >/dev/null 2>&1 &
```

В ходе занятия вы будете переводить задачи в фоновый режим (`&`), просматривать список заданий сессии (`jobs -l`), возвращать их на передний план (`fg`), приостанавливать (`Ctrl+Z`) и возобновлять в фоне (`bg`).

#### Разбор команд управления заданиями терминала:

| Команда / Флаг | Техническое описание и механика | Применение в эксплуатации и DevOps |
| :--- | :--- | :--- |
| `&` | Добавляется в конец команды для запуска процесса в фоновом режиме текущей сессии. | Запуск длительных задач или тестовых веб-серверов без блокировки командной строки. |
| `jobs -l` | Выводит список всех фоновых и приостановленных заданий сессии с их номерами и PID. | Позволяет узнать как номер задания (`%1`), так и системный PID для управления процессом. |
| `fg %<N>` | Переводит фоновое или приостановленное задание `<N>` на передний план терминала. | Возврат к взаимодействию с программой или просмотр ее живого вывода на экране. |
| `bg %<N>` | Возобновляет выполнение задачи, приостановленной комбинацией `Ctrl+Z`, в фоновом режиме. | Освобождает командную строку, если длительная задача была случайно запущена на переднем плане. |
| `nohup <команда> &` | Перенаправляет ввод/вывод и переводит обработчик `SIGHUP` в режим игнорирования. | Защищает длительные скрипты миграций и резервного копирования от сброса при разрыве SSH-сессии. |
| `bash -c '<строка>'` | Запускает дочернюю подоболочку для выполнения переданной строки команд. | Обязателен для передачи составных конструкций (циклов, пайпов) в `nohup`, `sudo` или systemd. |
| `disown -h %1` | Исключает запущенное фоновое задание из таблицы активных заданий оболочки. | Позволяет заданию, запущенному без `nohup`, пережить закрытие терминала без получения `SIGHUP`. |
| `jobs -p` | Выводит исключительно числовые идентификаторы PID фоновых заданий. | Применяется в bash-скриптах для сохранения PID дочерних задач в переменные. |
| `jobs -r` / `-s` | Фильтрует список заданий по состоянию: только работающие (`-r`) или только приостановленные (`-s`). | Быстрое обнаружение зависших задач, ожидающих пользовательского ввода. |

## Станция 3: Безопасность, права DAC и делегирование в Sudo

### Пример 3.1: Закон обхода каталогов

Выполните блок команд ниже для создания тестового каталога с файлом учетных данных базы данных:
```bash
# Создание защищенного каталога (-p: создавать родительские каталоги при отсутствии)
```

В ходе занятия вы установите на каталог права `644`, зафиксируете ошибку доступа при попытке чтения файла непривилегированным пользователем (`nobody`) и восстановите доступ, добавив бит выполнения `chmod +x` на родительский каталог.

#### Разбор масок прав доступа для `chmod`:

| Флаг / Маска | Техническое описание и механика | Применение в эксплуатации и DevOps |
| :--- | :--- | :--- |
| `644` (`rw-r--r--`) | Владелец имеет права на чтение/запись; группа и остальные только чтение. | Стандартный безопасный режим для конфигурационных файлов, веб-страниц и логов. |
| `+x` (`a+x`) | Добавляет бит выполнения (для файлов) или бит обхода и поиска (для каталогов). | Критичен для предоставления службам (например, `www-data`) права входа в каталог. |
| `-R` (--recursive) | Рекурсивно применяет изменение прав ко всей структуре каталогов и вложенных файлов. | Исправление прав на веб-директории (`chmod -R 755 /var/www/html`). |
| `--reference=<файл>` | Копирует точную маску прав с существующего эталонного файла на целевой объект. | Исключает ошибки ручного ввода при настройке идентичных прав в тестовом окружении. |
| `u+s` (`4000` SUID) | Программа выполняется с полномочиями владельца файла, а не запустившего ее пользователя. | Используется на системных утилитах (`/usr/bin/passwd`), требующих повышения прав до root. |
| `g+s` (`2000` SGID) | Каталоги обеспечивают групповое наследование: новые файлы получают группу каталога. | Стандарт для общих рабочих каталогов проектных команд разработки. |
| `+t` (`1000` Sticky) | Ограничивает право удаления файлов в каталоге только их владельцем или root. | Обязательный механизм защиты для общедоступных каталогов `/tmp` и `/var/tmp`. |

| `sudo -k` | Аннулирует кэш аутентификации sudo, требуя повторного ввода пароля. | Рекомендуется перед уходом от рабочего места или закрытием активной терминальной сессии. |

## Станция 4: Сокеты ядра, управление Systemd и веб-сервисы

### Пример 4.1: Анализ сокетов ядра с помощью `ss`

В этом упражнении вы будете использовать утилиту `ss` для анализа слушающих TCP и UDP сокетов, числового отображения адресов (`-n`) и фильтрации слушающих портов веб-сервера.

#### Разбор параметров утилиты `ss`:

| Флаг / Фильтр | Техническое описание и механика | Применение в эксплуатации и DevOps |
| :--- | :--- | :--- |
| `-t` (--tcp) | Фильтрует таблицу сокетов ядра только по протоколу TCP. | Изолирует веб-службы, базы данных и SSH-демоны, использующие надежное соединение TCP. |
| `-u` (--udp) | Фильтрует таблицу сокетов ядра только по протоколу UDP. | Показывает сервисы без подтверждения доставки: DNS-резолверы, службы NTP и DHCP. |
| `-n` (--numeric) | Отображает числовые адреса и порты, подавляя попытки преобразования имен через DNS. | Устраняет зависания при медленном DNS, обеспечивая мгновенный вывод данных при авариях. |
| `-l` (--listening) | Отображает только сокеты в состоянии `LISTEN`, отсекая активные клиентские соединения. | Отвечает на вопрос: «Какие службы в данный момент принимают входящие подключения?» |
| `-p` (--processes) | Показывает имя процесса и его PID, владеющий сокетом (требует прав суперпользователя). | Связывает открытый порт с конкретным процессом операционной системы. |
| `-a` (--all) | Отображает все сокеты: и слушающие, и установленные клиентские сессии. | Анализ количества активных внешних подключений клиентов к серверу. |
| `state established` | Фильтрует сокеты по состоянию TCP-соединения. | Точный анализ клиентского трафика на определенном порту без применения стороннего grep. |

### Пример 4.2: Локализация конфликта портов и анализ логов journald

Выполните блок команд ниже для моделирования конфликта портов путем запуска процесса Netcat на 80-м порту:
```bash
# Фоновый запуск netcat для удержания 80-го порта
# bash: -c — выполнить переданную строку команд
# nohup — игнорировать сигнал обрыва SIGHUP
# nc: -l — режим прослушивания, -p 80 — номер порта, -k — не закрывать сокет после завершения первого клиента
# & — перевод в фоновый режим
sudo bash -c 'nohup nc -l -p 80 -k >/dev/null 2>&1 &'
```

Выполните блок команд ниже для извлечения PID блокирующего процесса из статистики сокетов и его принудительного завершения:
```bash
# Извлечение PID процесса из вывода ss
# ss: -t — TCP, -u — UDP, -n — числовые порты, -l — слушающие сокеты, -p — показать PID и процесс
# awk: -F — указание разделителя полей для извлечения целевого токена
ROGUE_PID=$(sudo ss -tunlp | grep :80 | awk -F'pid=' '{print $2}' | awk -F',' '{print $1}')
# Принудительное уничтожение процесса ядром (kill: -9 — безусловный сигнал SIGKILL)
sudo kill -9 "$ROGUE_PID"
```

В ходе занятия вы попытаетесь запустить Nginx, зафиксируете отказ и прочитаете системный журнал `journalctl -xeu nginx --no-pager` для определения ошибки привязки адреса (`Errno 98 Address already in use`).

#### Разбор параметров `journalctl` и извлечения текста (`awk`):

| Флаг / Опция | Техническое описание и механика | Применение в эксплуатации и DevOps |
| :--- | :--- | :--- |
| `awk -F '<разделитель>'` | Задает разделитель полей (`-F'pid='`, `-F','`) и печатает изолированные токены (`{print $1}`). | Парсинг структурированного вывода системных утилит (`ss`, `/etc/passwd`, CSV-файлы). |
| `-x` (--catalog) | Дополняет записи журнала разъяснениями из каталога системных сообщений. | Помогает инженеру понять назначение системных кодов ошибок и содержит ссылки на документацию. |
| `-e` (--pager-end) | Мгновенно переходит в самый конец журнала для показа последних сообщений. | Показывает самые свежие сообщения об ошибках без необходимости долгой прокрутки. |
| `-u <юнит>` | Фильтрует журнал строго по указанному сервису Systemd (например, `-u nginx`). | Устраняет посторонний системный шум и изолирует логи конкретного упавшего приложения. |
| `--no-pager` | Выводит журнал напрямую в stdout без открытия интерактивной программы `less`. | Обязателен при работе в конвейерах, фильтрации через `grep` и запуске скриптов мониторинга. |
| `-f` (--follow) | Отслеживает и выводит новые записи журнала в реальном времени. | Применяется при развертывании релизов для наблюдения за ошибками запуска. |

### Пример 4.3: Сетевая диагностика: Уровень 4 (`nc`) против Уровня 7 (`curl`)

Выполните блок команд ниже для проверки числового кода ответа HTTP-сервера для скриптов мониторинга:
```bash
# Автоматизированное извлечение кода HTTP-ответа
# curl: -s — тихий режим (silent), -o /dev/null — подавить тело ответа, -w — форматированный вывод статуса
STATUS=$(curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:80)
echo "HTTP Response Status Code: $STATUS"
```

В ходе занятия вы выполните проверку TCP-рукопожатия на 4 уровне с помощью `nc -zv` и проверите прикладные HTTP-заголовки веб-сервера на 7 уровне с помощью `curl -I`.

#### Разбор параметров `nc` и `curl`:

| Команда и флаг | Техническое описание и механика | Применение в эксплуатации и DevOps |
| :--- | :--- | :--- |
| `nc -z` | Проверяет слушающие сокеты без передачи полезных прикладных данных. | Проверка доступности сетевого порта на 4 транспортном уровне модели OSI. |
| `nc -v` | Подробный вывод, сообщающий об успешном подключении или отказе в stderr. | Подтверждение факта завершения 3-стороннего рукопожатия TCP в терминале. |
| `curl -I` (--head) | Отправляет HTTP HEAD-запрос и выводит только служебные заголовки ответа. | Быстрая проверка HTTP-статуса (200, 301, 403, 500) и версии веб-сервера на 7 уровне. |
| `curl -s` (--silent) | Отключает вывод индикатора прогресса и сообщений об ошибках. | Предотвращает замусоривание вывода при сохранении ответа сервера в переменные скрипта. |
| `curl -o /dev/null` | Направляет тело ответа в системную «черную дыру» Linux. | Используется, когда требуются только заголовки или метрики времени, экономя память. |
| `curl -w "%{...}"` | Форматирует вывод и извлекает метрики сетевых задержек и статусов (`%{http_code}`). | Индустриальный стандарт для проверок доступности (synthetic health checks) в скриптах. |
| `nc -w <секунды>` | Задает максимальный таймаут ожидания сетевого соединения. | Предотвращает бесконечное зависание диагностических скриптов при потере пакетов. |
| `nc -u` | Переключает netcat в режим UDP для проверки сервисов без установления соединения. | Тестирование UDP-служб (DNS порт 53, NTP порт 123), где отсутствует рукопожатие TCP. |
| `nc -n` | Отключает DNS-запросы при подключении. | Ускоряет проверки портов и исключает сбои из-за таймаутов локальных серверов имен. |
| `curl -v` (--verbose) | Подробная трассировка рукопожатия. | Отображает DNS-разрешение, TCP-рукопожатие, согласование TLS-сертификатов и полные HTTP-заголовки. |
| `curl -k` (--insecure) | Игнорирует ошибки сертификатов SSL/TLS. | Позволяет тестировать HTTPS-эндпоинты с самоподписанными сертификатами в staging-окружениях. |
| `curl -L` (--location) | Автоматически следует по HTTP-редиректам. | Переходит по редиректам HTTP 301/302 к конечной странице (например, переход с `http://` на `https://`). |
| `curl -m <секунды>` | Максимальное общее время выполнения запроса. | Прерывает медленные HTTP-запросы в скриптах автоматизации при зависании ответа сервера. |
| `curl -H "Заголовок: Знач"` | Добавляет пользовательские HTTP-заголовки. | Тестирование маршрутизации виртуальных хостов (например, `curl -H "Host: api.company.com" http://127.0.0.1`). |
| `curl -d '<данные>' -X POST` | Отправляет полезную нагрузку методом HTTP POST. | Используется в автоматизации для передачи JSON-данных или вызова вебхуков. |

#### Разбор метрик статуса и диагностики `curl -w` (--write-out):

Опция `-w` / `--write-out` форматирует вывод с использованием системных переменных процесса передачи (`%{имя_переменной}`):

| Идентификатор переменной | Описание извлекаемой метрики | Применение в эксплуатации и DevOps |
| :--- | :--- | :--- |
| `%{http_code}` | Числовой код HTTP(S)-статуса ответа сервера (например, `200`, `301`, `403`, `502`). | Автоматизированные проверки доступности, алерты мониторинга и тесты в CI/CD. |
| `%{response_code}` | Протоколонезависимый числовой код ответа (синоним `http_code`). | Универсальное извлечение статуса для протоколов HTTP, FTP и других. |
| `%{http_version}` | Согласованная версия протокола HTTP (`1.1`, `2`, `3`). | Проверка корректности апгрейда протокола до HTTP/2 или HTTP/3 за балансировщиком нагрузки. |
| `%{content_type}` | Значение заголовка `Content-Type` ответа сервера (например, `application/json`, `text/html`). | Проверка возврата ожидаемого MIME-типа микросервисом вместо HTML-страницы с ошибкой. |
| `%{remote_ip}` | IP-адрес удаленного сервера или прокси, ответившего на соединение. | Подтверждение направления трафика на нужный узел или edge-сервер CDN, исключая старые DNS-записи. |
| `%{remote_port}` | Номер удаленного порта, на который установлено подключение (`80`, `443`, `8080`). | Проверка корректности проброса портов, правил обратного прокси или маппинга в контейнерах. |
| `%{time_namelookup}` | Время (в секундах) от старта запроса до завершения DNS-разрешения имени. | Локализация задержек при медленной работе DNS-серверов или ошибках в `/etc/resolv.conf`. |
| `%{time_connect}` | Время (в секундах) от начала запроса до завершения 3-стороннего рукопожатия TCP. | Измерение задержки на сетевом транспортном уровне между клиентом и сервером. |
| `%{time_appconnect}` | Время (в секундах) от старта до завершения рукопожатия SSL/TLS. | Локализация медленного согласования TLS, нагрузки на шифрование или межрегиональных задержек. |
| `%{time_starttransfer}` | Время (в секундах) до получения первого байта ответа от сервера (TTFB). | Оценка скорости обработки запроса бэкенд-приложением и задержек базы данных. |
| `%{time_total}` | Общее время выполнения транзакции (в секундах) от старта до завершения передачи. | Контроль выполнения соглашений об уровне обслуживания (SLA) и бенчмаркинг задержек пользователей. |
| `%{size_download}` | Общий объем загруженных полезных данных в байтах по HTTP-соединению. | Проверка сжатия данных, целостности полезной нагрузки и потребления сетевой полосы. |
| `%{speed_download}` | Средняя скорость загрузки в байтах в секунду. | Мониторинг узких мест пропускной способности сети и производительности передачи файлов. |
| `%{redirect_url}` | Целевой URL-адрес из заголовка ответа HTTP 301/302 `Location`. | Аудит циклов редиректов, маршрутизации канонических доменов и правил перехода с HTTP на HTTPS. |
| `%{num_redirects}` | Количество переходов по редиректам при использовании флага `-L` (--location). | Обнаружение избыточных цепочек редиректов, замедляющих загрузку страниц. |
| `%{ssl_verify_result}` | Результат проверки SSL-сертификата (`0` означает валидный и доверенный сертификат). | Автоматизированный аудит валидности сертификатов, сроков их действия и цепочек доверия CA. |

### Пример 4.4: Маскирование служб и управление жизненным циклом в Systemd

В этом упражнении вы разберете практическую разницу между остановкой, отключением автозапуска и полным маскированием служб в менеджере Systemd.

> [!NOTE]
> **Механика маскирования служб в Systemd (`stop` против `disable` против `mask`):**
> - `systemctl stop <юнит>`: Немедленно останавливает активный процесс, но позволяет перезапустить его вручную или через зависимость в любой момент.
> - `systemctl disable <юнит>`: Удаляет симлинки автозапуска из `/etc/systemd/system/*.wants/`, предотвращая запуск при старте системы. Однако службу по-прежнему можно запустить вручную (`systemctl start`) или автоматически, если ее требует другая служба (`Wants=` или `Requires=`).
> - `systemctl mask <юнит>`: Самый жесткий механизм блокировки в systemd. Он создает символическую ссылку в `/etc/systemd/system/<юнит>` на `/dev/null`. Поскольку `/etc/systemd/system/` имеет приоритет над каталогами пакетов в `/lib/systemd/system/`, systemd считает юнит недействительным и отказывается запускать его при любых условиях (вручную, при загрузке или по триггеру зависимости).
> - `systemctl unmask <юнит>`: Удаляет симлинк на `/dev/null`, возвращая исходную конфигурацию юнита и штатный режим работы.

#### Разбор команд управления в `systemctl`:

| Команда / Опция | Техническое описание и механика | Применение в эксплуатации и DevOps |
| :--- | :--- | :--- |
| `mask <юнит>` | Связывает конфигурацию юнита с `/dev/null`, делая его запуск невозможным для пользователей и демонов. | Предотвращает случайный запуск конфликтующих демонов во время технических работ или миграций. |
| `unmask <юнит>` | Удаляет символическую ссылку на `/dev/null`, восстанавливая возможность запуска юнита. | Возвращает службу в штатный режим управления после завершения обслуживания или разрешения конфликта. |
| `restart <юнит>` | Останавливает процесс службы и запускает новый экземпляр по файлу юнита. | Применение серьезных изменений, сброс кэша или перезапуск зависшего процесса. |
| `is-active <юнит>` | Возвращает код выхода 0, если служба работает; выводит `active` или `inactive`. | Надежная условная проверка в скриптах (`if systemctl is-active --quiet nginx; then ...`). |
| `reload <юнит>` | Посылает сигнал перечитать конфигурацию без разрыва клиентских соединений. | Бесперебойный деплой конфигураций обратных прокси и веб-серверов (`systemctl reload nginx`). |
| `enable` / `disable` | Создает или удаляет симлинки в каталогах автозагрузки `/etc/systemd/system/*.wants/`. | Управление автоматическим стартом сервисов при плановой или аварийной перезагрузке хоста. |
| `is-enabled <юнит>` | Программно проверяет статус включения в автозапуск (код выхода 0, если включен). | Использование в скриптах инициализации (Ansible/Bash) для подтверждения автозапуска критичных демонов. |
| `list-units --type=service` | Выводит список всех активных юнитов systemd с фильтрацией по типу `service`. | Аудит фоновых служб, загруженных и работающих на хосте в данный момент. |
| `daemon-reload` | Перечитывает конфигурационные файлы юнитов в `/etc/systemd/system/` и `/lib/systemd/system/`. | Обязательный шаг после создания, изменения или переопределения любого `.service`-файла на диске. |
| `cat <юнит>` | Выводит полное содержимое файла юнита со всеми активными переопределениями (drop-ins). | Показывает точные команды запуска (`ExecStart`), политики перезапуска и файлы окружения без поиска по диску. |

## Команды очистки лабораторного стенда

Выполните блок команд ниже для удаления всех временных каталогов, тестовых пользователей и конфигураций, созданных в процессе выполнения лабораторной работы:
```bash
# Удаление временных файлов и каталогов (rm: -r — рекурсивно, -f — принудительно без запросов)
sudo rm -rf /tmp/app_logs /tmp/urgent_alerts.txt /tmp/alerts.tar.gz /tmp/incident_logs.tar.gz /tmp/secure_vault /tmp/app_staging /tmp/output.log /tmp/error.log /tmp/combined.log /tmp/sync.log /etc/sudoers.d/dev_alex_nginx

# Завершение сессий тестового пользователя через loginctl
sudo loginctl terminate-user dev_alex 2>/dev/null || true
# Завершение всех процессов пользователя (pkill: -u dev_alex — процессы пользователя dev_alex, -9 — сигнал SIGKILL)
sudo pkill -u dev_alex -9 2>/dev/null || true
# Удаление пользователя с домашней директорией (userdel: -r — удалить домашний каталог и почтовый ящик)
sudo userdel -r dev_alex 2>/dev/null || true
sudo groupdel devops_team 2>/dev/null || true

# Перезапуск веб-сервера Nginx и проверка заголовков HTTP-ответа (curl: -I — отправка метода HEAD, только заголовки)
sudo systemctl restart nginx
curl -I http://127.0.0.1:80
```
