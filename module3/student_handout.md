## 1. 4-уровневая модель TCP/IP

Современные компьютерные сети и облачная инфраструктура функционируют на базе практической 4-уровневой модели протоколов TCP/IP:

1. **Прикладной уровень (Application Layer):** Протоколы верхнего уровня, с помощью которых программы обмениваются структурированными данными через сеть (HTTP, HTTPS, SSH, DNS, SMTP).
2. **Транспортный уровень (Transport Layer):** Обеспечивает сквозное взаимодействие между процессами на хостах. Управляет номерами портов (0–65535) и определяет гарантии доставки данных (TCP, UDP).
3. **Межсетевой уровень (Internet Layer):** Отвечает за логическую адресацию, формирование сетевых пакетов и маршрутизацию между сетями (IPv4, IPv6, ICMP).
4. **Уровень сетевого доступа / канальный уровень (Network Access / Link Layer):** Обеспечивает физическую передачу сигналов по локальным кабелям, оптоволокну или радиоканалам с использованием аппаратных MAC-адресов сетевых карт (Ethernet, Wi-Fi).

![4-уровневая архитектура TCP/IP и инструменты DevOps](../../assets/module3/tcp_ip_network_layers.png)

### Сравнение протоколов TCP и UDP
- **TCP (Transmission Control Protocol):** Протокол с установлением соединения, гарантирующий надежную и упорядоченную доставку данных. Перед передачей данных выполняется трехстороннее рукопожатие (3-way handshake: `SYN` $\rightarrow$ `SYN-ACK` $\rightarrow$ `ACK`). Потерянные пакеты отправляются повторно при подтверждении тайм-аута. Используется для веб-сервисов (HTTP/HTTPS), удаленного управления (SSH) и баз данных.
- **UDP (User Datagram Protocol):** Протокол без установления соединения, легковесный и быстрый ("отправил и забыл"). Минимальный заголовок, отсутствие рукопожатий и подтверждений доставки. Используется для DNS-запросов (порт 53), потокового видео, телеметрии метрик и VoIP.

> [!NOTE]
> В Kubernetes и микросервисных архитектурах сетевое взаимодействие между подами организуется через оверлейные сети (например, Calico или Cilium), инкапсулирующие IP-пакеты 3-го уровня в виртуальные туннели. Независимо от физической инфраструктуры приложения продолжают использовать стандартные транспортные сокеты TCP/IP.

## 2. Архитектура DNS и типы ресурсных записей

Система доменных имен (DNS) преобразует понятные человеку доменные имена в числовые IP-адреса, используемые маршрутизаторами в сети.

### Основные типы записей DNS
- **A:** Сопоставляет имя хоста с 32-битным адресом IPv4 (`example.com -> 93.184.216.34`).
- **AAAA:** Сопоставляет имя хоста со 128-битным адресом IPv6.
- **CNAME (Canonical Name):** Канонический псевдоним, перенаправляющий одно доменное имя на другое (`www.example.com -> example.com`).
- **MX (Mail Exchange):** Определяет почтовые серверы, принимающие входящую почту для данного домена.
- **TXT:** Хранит текстовые метаданные, используемые для подтверждения владения доменом и защиты от спама/подделки почты (SPF, DKIM, DMARC).
- **PTR (Pointer):** Запись обратного DNS-поиска, преобразующая IP-адрес обратно в доменное имя.

### Иерархия выполнения DNS-запросов
Разрешение доменного имени проходит по иерархическому дереву делегирования:
Рекурсивный резолвер (например, `8.8.8.8`) $\rightarrow$ Корневые DNS-серверы (`.`) $\rightarrow$ Серверы доменов верхнего уровня TLD (`.com`) $\rightarrow$ Авторитативный DNS-сервер домена.

## 3. Команды диагностики DNS (`dig`)

Инженеры DevOps и SRE используют утилиту `dig` (Domain Information Groper) для тестирования DNS-серверов и расследования сетевых сбоев:

- `dig [домен]` — Стандартный запрос; анализируйте секцию `ANSWER SECTION` и значение Time-To-Live (TTL).
- `dig +short [домен]` — Вывод только целевого IP-адреса без метаданных (оптимально для автоматизации и скриптов).
- `dig [домен] [тип_записи]` — Запрос конкретного типа записи (`dig google.com MX`, `dig google.com TXT`).
- `dig @[ip_резолвера] [домен]` — Прямой запрос к конкретному вышестоящему DNS-серверу (например, `dig @1.1.1.1 google.com`).
- `dig [домен] +trace` — Трассировка полного пути запроса от корневых серверов до авторитативного источника.
- `dig -4 @[ip_резолвера] [домен] +trace` — Принудительное использование протокола IPv4 при трассировке для предотвращения ошибок недоступности IPv6.
- `dig -x [ip_адрес]` — Обратный DNS-запрос для получения PTR-записи по IP-адресу.

> [!TIP]
> Всегда обращайте внимание на второй столбец секции `ANSWER SECTION` в выводе `dig`: это значение TTL (Time-To-Live) в секундах. Перед миграцией продакшн-серверов или сменой IP-адресов уменьшайте TTL до 300 секунд (5 минут) за несколько дней до работ, чтобы ускорить распространение изменений.

## 4. IP-адресация, нотация CIDR и частные подсети RFC 1918

Каждый сетевой узел требует уникальный IP-адрес для взаимодействия на 3-м уровне модели:
- **IPv4:** 32-битный адрес, разделенный на 4 десятичных октета (`0.0.0.0` – `255.255.255.255`).
- **IPv6:** 128-битный шестнадцатеричный адрес (`2001:0db8:...`).

### Нотация CIDR (Длина префикса)
Суффикс через косую черту указывает, сколько бит из 32 зафиксировано под адрес сети (Network ID):
- `/32` — Ровно один конкретный хост (например, `192.168.1.50/32`).
- `/24` — Зафиксировано 24 бита (`255.255.255.0`), 8 бит остается для хостов ($2^8 = 256$ адресов всего, 254 доступно для узлов). Стандартная локальная сеть.
- `/20` — Зафиксировано 20 бит (`255.255.240.0`), 12 бит для хостов ($2^{12} = 4096$ адресов всего, 4094 доступно). Типичный размер подсети в облачных VPC и WSL 2 NAT.
- `/0` — Маска охватывает все адресное пространство IPv4 (`0.0.0.0/0`). Применяется для записи шлюза по умолчанию (Default Gateway).

### Частные диапазоны RFC 1918 (Не маршрутизируются в интернете)
Частные подсети изолированы от глобального интернета и требуют шлюзов NAT (Network Address Translation) для выхода наружу:
- `10.0.0.0` – `10.255.255.255` (Класс A: Корпоративные сети предприятий, облачные VPC).
- `172.16.0.0` – `172.31.255.255` (Класс B: Контейнерные мосты Docker, подсети WSL 2 NAT).
- `192.168.0.0` – `192.168.255.255` (Класс C: Домашние роутеры, локальные офисные сети).
- `127.0.0.1` — **Петлевой интерфейс (`localhost`)**: Локальный сетевой стек внутри ядра операционной системы.

## 5. Сетевые интерфейсы и маршрутизация (`ip`)

Пакет `iproute2` является современным стандартом управления сетями в Linux, заменяющим устаревшие утилиты `ifconfig`, `netstat` и `route`:

- `ip link show` — Список физических и виртуальных интерфейсов, состояние соединения (`UP`/`DOWN`) и MAC-адреса.
- `ip a` (или `ip addr show`) — Отображение всех назначенных IPv4 и IPv6 адресов с масками подсетей CIDR.
- `ip -br a` — Компактный однострочный вывод активных интерфейсов и их IP-адресов.
- `ip r` (или `ip route show`) — Таблица маршрутизации ядра Linux.
  - Строка, начинающаяся с `default via [ip_шлюза]`, определяет **шлюз по умолчанию** (Default Gateway).
- `hostname -I` — Вывод всех локальных IP-адресов хоста через пробел.
- `curl -s ifconfig.me` — Определение внешнего публичного IP-адреса через публичный сервис отражения.

## 6. Порты и сетевые сокеты

**Сетевой порт** (от 0 до 65535) — это 16-битное число, идентифицирующее конкретный процесс приложения, принимающий входящие пакеты:

- **0 – 1023 (Привилегированные / системные порты):** Требуют прав суперпользователя `root` или capability `CAP_NET_BIND_SERVICE` для открытия.
  - Порт 22: SSH (Безопасный удаленный доступ)
  - Порт 53: DNS (Служба доменных имен)
  - Порт 80: HTTP (Нешифрованный веб-трафик)
  - Порт 443: HTTPS (Зашифрованный веб-трафик TLS/SSL)
- **1024 – 49151 (Зарегистрированные порты):** Используются пользовательскими службами и серверами баз данных (3306 MySQL, 5432 PostgreSQL, 6379 Redis, 8080 альтернативный веб-порт).
- **49152 – 65535 (Динамические / эфемерные порты):** Временные порты, выделяемые ядром Linux для исходящих клиентских подключений.

### Привязка к интерфейсам (Socket Binding)
- `127.0.0.1:80` — Служба слушает только петлевой интерфейс. Подключение возможно **исключительно** с программ на этом же локальном сервере.
- `0.0.0.0:80` (или `*:80`) — Служба привязана ко **всем** сетевым интерфейсам. Доступ открыт для внешних машин из сети.

## 7. Диагностика сокетов с помощью `ss`

Утилита `ss` (Socket Statistics) опрашивает структуры ядра Linux через сокеты netlink, обеспечивая быстрый анализ открытых портов:

- `sudo ss -tunlp` — Список всех слушающих TCP и UDP сокетов с именами процессов и их PID.
  - `-t`: Сокеты TCP
  - `-u`: Сокеты UDP
  - `-n`: Числовой формат IP и портов (без замедляющих обратных DNS-запросов)
  - `-l`: Только слушающие сокеты (Listening)
  - `-p`: Имя процесса и его идентификатор PID (требует `sudo`)
- `sudo ss -tunlp | grep :80` — Фильтрация сокетов, слушающих порт 80.
- `ss -ta` — Отображение всех TCP-сокетов (как слушающих, так и установленных соединений).
- `ss -s` — Сводная статистика по сокетам и распределению памяти.

## 8. Жизненный цикл служб Systemd (`systemctl`)

Systemd — основной менеджер системы и служб (PID 1) во всех современных дистрибутивах Linux.

![Жизненный цикл служб Systemd и управление процессами](../../assets/module3/systemd_service_lifecycle.png)

### Управление службами в оперативной памяти
- `sudo systemctl start [служба]` — Немедленный запуск службы в оперативной памяти.
- `sudo systemctl stop [служба]` — Корректная остановка дерева процессов службы.
- `sudo systemctl restart [служба]` — Перезапуск службы (остановка и повторный запуск).
- `sudo systemctl reload [служба]` — Перечитывание файлов конфигурации без разрыва активных соединений клиентов.
- `systemctl status [служба]` — Просмотр состояния, активного PID, дерева cgroups и последних записей логов.
- `systemctl is-active [служба]` — Проверка активности службы (`active` или `inactive`).

### Управление автозагрузкой
- `sudo systemctl enable [служба]` — Включение автоматического запуска службы при старте системы.
- `sudo systemctl disable [служба]` — Отключение автозапуска службы.
- `systemctl is-enabled [служба]` — Проверка статуса автозагрузки (`enabled` или `disabled`).
- `sudo systemctl enable --now [служба]` — Одновременный запуск службы и добавление ее в автозагрузку одной командой.
- `sudo systemctl daemon-reload` — Перечитывание конфигураций systemd после изменения или создания unit-файлов.
- `systemctl list-units --type=service --state=running` — Вывод всех запущенных системных служб.

## 9. Развертывание веб-сервера: Nginx

Nginx — отраслевой стандарт высокопроизводительного обратного прокси-сервера и веб-сервера HTTP.

Команды ниже устанавливают пакет веб-сервера Nginx, запускают его службу под управлением systemd, добавляют в автозапуск и проверяют активность сокета:

```bash
# 1. Обновление индексов пакетов и установка Nginx
sudo apt update && sudo apt install -y nginx

# 2. Запуск службы и включение в автозагрузку одной командой
sudo systemctl enable --now nginx

# 3. Проверка прослушивания порта 80
sudo ss -tunlp | grep :80
```

По умолчанию статический контент веб-страниц отдается из каталога `/var/www/html/index.nginx-debian.html`.

![Диагностическая модель Outside-In для веб-запросов](../../assets/module3/nginx_request_flow_outside_in.png)

### Диагностический чек-лист Outside-In
При недоступности веб-сервиса расследование проводится последовательно снаружи внутрь:

1. **Проверка клиентом (`curl -I http://<ip>`):** Определение характера сбоя: тайм-аут (файрвол отбрасывает пакеты), сброс соединения `Connection refused` (порт не слушается) или ошибка 500/502 (сбой приложения).
2. **Периметр безопасности (`sudo ufw status`):** Проверка разрешения входящего трафика на порты 80/443.
3. **Привязка сокета (`sudo ss -tunlp | grep :80`):** Проверка состояния сокета `LISTEN` и привязки к `0.0.0.0` (или `*:80`), а не только к `127.0.0.1`.
4. **Состояние службы (`sudo systemctl status nginx`):** Проверка статуса unit-файла (`active (running)` или `failed`).
5. **Синтаксис и журналы (`nginx -t` и `sudo journalctl -u nginx -n 20`):** Проверка синтаксиса конфигурационных файлов и анализ системных логов.
6. **Права файловой системы (`ls -ld /var/www/html/*`):** Проверка прав пользователя `www-data` на чтение файлов и выполнение (`+x`) для прохода по родительским каталогам.

## 10. Инструменты веб-диагностики и проверки сетевой связности

### `curl` (Client URL)
- `curl [url]` — Выполнение HTTP GET-запроса и вывод тела ответа в stdout.
- `curl -I [url]` — Запрос только заголовков HTTP (проверка статус-кода ответа и заголовка Server).
- `curl -v [url]` — Подробный режим: вывод этапов DNS-поиска, TCP-рукопожатия и обмена заголовками.
- `curl -s [url]` — Тихий режим без индикатора прогресса (для использования в скриптах).
- `curl -o [файл] [url]` — Сохранение ответа в указанный локальный файл.
- `curl -O [url]` — Скачивание удаленного файла с сохранением оригинального имени.
- `curl -L [url]` — Автоматический переход по редиректам HTTP (301 / 302).
- `curl -k [url]` — Разрешение небезопасных соединений SSL/TLS (игнорирование предупреждений самоподписанных сертификатов).

### `nc` (Netcat)
- `nc -zv [хост] [порт]` — Проверка доступности TCP-порта на транспортном уровне без отправки данных прикладного уровня.
  - *Пример:* `nc -zv localhost 80`
  - *Совет DevOps:* Используйте `nc -zv` для проверки доступности порта на 4-м уровне до начала поиска ошибок в коде приложения на 7-м уровне.

### `ping` и диагностика маршрутов (`mtr`)
- `ping -c [число] [хост]` — Отправка пакетов ICMP Echo Request для проверки сетевой связности на 3-м уровне.
  - *Предупреждение:* Многие облачные провайдеры и файрволы блокируют ICMP-пакеты, пропуская при этом TCP-трафик.
- `mtr -t [хост]` — Объединенная утилита ping и traceroute в терминальном режиме для выявления потерь пакетов на промежуточных узлах.

## 11. Работа с системным журналом Systemd (`journalctl`)

Systemd объединяет логи служб и ядра в единый бинарный журнал journald:

- `sudo journalctl -u [служба]` — Вывод всех логов конкретной службы.
- `sudo journalctl -xeu [служба]` — Логи с пояснениями из каталога ошибок в конце файла (для оперативной диагностики сбоев).
- `sudo journalctl -u [служба] -f` — Потоковый вывод новых сообщений службы в реальном времени.
- `sudo journalctl -u [служба] -n [число] --no-pager` — Вывод последних $N$ строк без перехода в интерактивный постраничный просмотр.
- `sudo journalctl -u [служба] --since "15 minutes ago"` — Фильтрация записей по временному диапазону.
